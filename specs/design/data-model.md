# Data model

Chunks already exist in `chunks_onbv.jsonl`, generated by the chunking
script. Each line:

```json
{
  "id": "GEN_1_1-5",
  "ref": "GEN 1:1-5",
  "book": "GEN",
  "chapter": 1,
  "verse_start": 1,
  "verse_end": 5,
  "word_count": 65,
  "text": "No princípio Deus criou os céus e a terra. ..."
}
```

- `book` uses the **USFM** book code (GEN, EXO, ..., MAT, JHN, ..., REV).
- `id` is stable and deterministic (book + chapter + range) and fits the
  Vectorize 64-byte limit. Using the JSONL `id` as the vector ID makes
  upserts idempotent (as long as chunk boundaries do not change).
- `id` format: a chunk with several verses is `BOOK_CHAPTER_START-END`
  (`GEN_1_1-5`); a **single-verse chunk** is `BOOK_CHAPTER_VERSE`
  (`GEN_14_24`, no `-END`). The Worker must not assume the id can be
  computed from a verse number: use the metadata filter lookup in the
  [query flow](../flows/query.md).
- `ref`/`verse_start`–`verse_end` describe the range, which may include
  verse numbers absent from the source itself (e.g. a verse omitted by the
  translation); do not assume every number in the range has text.

## Book table

`src/books.ts`, shared with ingestion: maps USFM code → Portuguese name,
canonical order and testament.

```ts
export const BOOKS = {
  GEN: { code: "GEN", name: "Gênesis", order: 1,  testament: "AT" },
  JHN: { code: "JHN", name: "João",    order: 43, testament: "NT" },
  // ... 66 books
} as const satisfies Record<string, Book>;

export const BOOK_CODES = Object.keys(BOOKS) as [BookCode, ...BookCode[]]; // for z.enum
```

Displayed reference: `GEN 1:1-5` → **Gênesis 1:1-5**; a single verse →
**João 3:16**.

## Metadata stored in Vectorize per vector

| Field | Type | Indexed? | Use |
| ----- | ---- | -------- | --- |
| `book` | string | yes | filter by book |
| `testament` | string | yes | filter OT/NT |
| `chapter` | number | yes | filter by chapter |
| `verse_start` | number | yes | build reference; find the chunk containing a verse (`<=` filter) |
| `verse_end` | number | no | build reference |
| `ref` | string | no | canonical reference |
| `text` | string | no | text returned to the LLM and API client |
| `translation` | string | no | always `"ONBV"` |

Storing `text` in metadata avoids an extra database: with up to 120 words,
each chunk is well under the 10 KiB limit. **Create metadata indexes before
inserting vectors**, because vectors inserted earlier are not indexed. Four
indexes (`book`, `testament`, `chapter`, `verse_start`) stay within the
limit of 10.

## Attribution constant

The attribution notice lives in **one place**: `ATTRIBUTION.md` is the
human-readable source, and `src/attribution.ts` holds the same
text as a constant (the Worker cannot read repository files at runtime).
`ATTRIBUTION.md` also holds provenance and transformation details, so the
text served by the API (the `notice` and `changes` fields) sits between the
markers `<!-- attribution:start -->` and `<!-- attribution:end -->`. A test
compares the constant with the text between those markers so they cannot
drift.
